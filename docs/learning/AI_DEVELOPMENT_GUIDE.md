# ArduSub 教学仓库：AI 接手开发指南与提示词

> 本文是写给后续智能体、AI 编程工具和新加入开发者的项目交接说明。
>
> 它不能代替真实源码，也不能代替飞控安全测试。遇到本文与当前源码不一致时，应先以当前源码为事实依据，再把已经确认的变化更新回本文。

## 1. 你正在维护什么

这是一个以官方 ArduPilot/ArduSub 为基础的教学与二次开发仓库。目标不是重新发明一套飞控，也不是把所有公共库改写成看似简单的小程序，而是：

1. 保留完整、真实、可编译的 ArduSub 功能主线；
2. 用中文解释大型 C++、Waf、MAVLink、调度器、HAL、控制器和推进器输出；
3. 让只具备 C++ 入门语法的学习者能沿调用链理解系统；
4. 在理解官方实现以后，小步完成传感器、控制模式、通信协议和板卡适配；
5. 所有裁剪和二次开发都必须有可重复的编译或测试证据。

不要把“最简”理解成“文件越少越好”。本项目中的“最简”是：学习入口清晰、当前车辆主线清晰、修改范围可控，同时不破坏官方依赖关系和安全机制。

## 2. 开始工作前必须阅读

按照以下顺序建立上下文：

1. 根目录 `AGENTS.md`：不可违反的安全、风格、测试和提交规则；
2. 根目录 `README.md`：仓库目的、结构和编译方法；
3. `docs/learning/README.md`：20 章课程地图；
4. 与任务相关的章节；
5. 章节列出的真实 `.h`、`.cpp`、`wscript`、XML 或 `hwdef.dat`；
6. 当前 `git status` 和 `git diff`：确认哪些修改已经属于用户。

不能仅凭文件名猜测实现，也不能仅依据通用 ArduPilot 经验断言本仓库当前版本的行为。所有接口、枚举、参数和调用关系都应在当前源码中核实。

## 3. 已确认的项目边界

### 3.1 车辆和板卡

- 主要车辆只有 **ArduSub**；不要引入其他车辆源码作为新的产品主线。
- 当前首要板卡是 **Pixhawk 2.4.8**，在构建系统中使用 `Pixhawk1`/`fmuv3` 相关定义。
- 未来可能迁移到 Pixhawk6 等新板卡，因此车辆层不能直接绑定 STM32 寄存器或某一块板的引脚。
- 固件输出仍通过 ArduPilot HAL、ChibiOS 和 `hwdef.dat` 完成。

### 3.2 传感器和状态估计

- 当前明确使用的压力/深度传感器是 **MS5837**。
- 暂不把 GPS 和外部罗盘作为当前小脑的必需输入。
- DVL 与 USBL 需要预留两种接入方式：
  1. 由香橙派处理后，通过 MAVLink 向 Pixhawk 提供外部里程计或定位信息；
  2. 设备通过 UART 直接接入 Pixhawk，并由真实、经过验证的后端驱动解析。
- 当前源码没有一个可以凭空套用的通用 `AP_DVL` 驱动。实现 UART 直连前，必须先获得设备协议、数据频率、坐标定义、时间戳和质量字段。
- 使用 MAVLink `ODOMETRY` 时必须核对当前源码接受的坐标系、姿态、速度、协方差、质量、复位计数和时间语义，不能只把数值填入同名字段。

### 3.3 大小脑分工

- 香橙派负责高层感知、多传感器融合、环境理解和持续目标规划。
- Pixhawk/ArduSub 负责可靠的状态接入、模式管理、姿态/深度/位置控制、推进器分配、解锁和故障保护。
- 高层可以持续向 Guided 等模式发送目标，但不得绕过飞控的解锁、模式约束和失控保护。
- **保留 Auto 模式**，因为将来仍可能执行水面航点或任务巡航。
- 避免同一份 DVL/USBL 信息同时以多个来源重复进入 EKF，造成重复融合和虚假置信度。

### 3.4 MAVLink 策略

- 默认继续使用仓库已有 MAVLink 模块和 XML，不为“看起来整洁”而修改生成文件。
- `ardusub.xml` 或协议梳理文档可以用于学习，但不能冒充上游协议的唯一事实来源。
- 真正增加自定义消息时，应修改合适的 MAVLink dialect XML，分配不冲突的消息 ID，重新生成代码，同时实现发送端、接收端和地面站/伴随计算机支持。
- `modules/mavlink` 是子模块。除非任务明确要求维护对应上游子模块，否则不要直接把生成头文件或临时修改提交到主仓库。

## 4. 与用户协作时的教学约定

用户希望理解每一次修改，而不只是得到最终代码。每批操作之前都要先用通俗中文说明：

1. 当前准备解决什么问题；
2. 为什么现在要看或改这些文件；
3. 数据从哪里来、将到哪里去；
4. 预计只会影响哪些文件；
5. 完成后用什么办法证明没有破坏原系统。

每批改动应尽量小，使学习者能同时看到“修改前—原因—修改后—验证结果”。不要一次复制几十个目录、一次删除大量驱动，或连续修改很多互不相关的模块。

讲解源码时，默认读者只掌握 C++ 基础语法。遇到继承、虚函数、回调、模板、宏、单例、条件编译和对象生命周期，应先解释它解决的工程问题，再解释语法。

推荐使用下面的讲解结构：

```text
现实问题
    ↓
本层的输入
    ↓
核心类或函数
    ↓
本层的输出
    ↓
下一层由谁接收
```

必须区分三类信息：

- **源码事实**：可以给出文件、类、函数或配置作为证据；
- **工程推断**：根据当前调用关系得出的判断，应明确写成推断；
- **尚缺信息**：例如未知传感器协议或板卡原理图，不能用想象补齐。

## 5. 每个开发任务的标准流程

### 第一步：界定一条主线

把任务写成一条能验证的数据流，例如：

```text
DVL UART 字节
    → 新后端解析
    → 坐标与时间转换
    → ExternalNav 接口
    → EKF
    → Guided 位置控制
```

如果不能画出输入、输出和所有权，先不要写代码。

### 第二步：寻找当前真实实现

优先搜索以下内容：

- 对象在哪里声明、在哪里构造；
- 谁调用目标函数；
- 功能受哪个 `#if AP_*_ENABLED` 控制；
- 参数在哪里登记、索引是否已经占用；
- 对应库如何进入 `ArduSub/wscript` 的依赖；
- 是否已有同类型后端、模式或消息可以作为模板。

借用官方代码时，应解释借用了哪个抽象或生命周期，而不是机械复制整个目录。

### 第三步：提出最小改动

修改前列出文件清单及其职责。优先复用已有 frontend/backend、模式基类、HAL、MAVLink 路由和参数系统。不要在车辆层直接操作 UART 寄存器、PWM 寄存器或板级 GPIO。

对于安全关键逻辑，应先写清以下约束：

- 未解锁时会发生什么；
- 输入超时或质量下降时会发生什么；
- 模式切换失败时会发生什么；
- 单位、坐标系、符号和有效范围是什么；
- 旧参数和旧日志是否仍兼容。

### 第四步：小步实现并解释

一次只完成一个可以编译的闭环。每段新增代码都要说明：

- 为什么属于这个类；
- 谁拥有它以及生命周期多长；
- 谁会调用它；
- 输入输出单位；
- 正常路径和失败路径；
- 为什么没有放到其他层。

不要为了“中文化”删除仍然有价值的上游英文注释，也不要给每一行添加重复语法的注释。完整原理写入 `docs/learning/`，源码注释只解释容易误解的设计意图、单位、坐标系和安全约束。

### 第五步：按风险验证

最小验证顺序如下：

1. 检查修改范围：`git status --short`、`git diff --stat`、`git diff`；
2. 检查空白和补丁错误：`git diff --check`；
3. 配置并编译 SITL；
4. 运行与功能相关的单元测试或 ArduSub SITL 场景；
5. 配置并编译 Pixhawk1；
6. 硬件相关修改经过断桨/断电机台架验证；
7. 最后才允许受控水池测试和真实水域测试。

构建成功只能证明代码能够形成固件，不能证明控制方向、坐标系、故障保护或硬件接线正确。没有实际执行的测试必须明确写成“未测试”。

## 6. 当前仓库的常用构建命令

所有命令从 WSL 仓库根目录 `/home/pzy/ArduSub` 执行，禁止使用 `sudo ./waf`。

```bash
# SITL
./waf configure --board sitl
./waf sub -j4

# Pixhawk 2.4.8 / Pixhawk1
./waf configure --board Pixhawk1
./waf sub -j4

# 查看目标和清理当前构建配置
./waf list
./waf clean
```

当前机器如果没有自动加载 Python 虚拟环境和 ARM 工具链，可以显式使用已经验证过的路径：

```bash
env PATH=/home/pzy/venv-ardupilot/bin:/opt/gcc-arm-none-eabi-10-2020-q4-major/bin:$PATH \
    ./waf configure --board Pixhawk1
env PATH=/home/pzy/venv-ardupilot/bin:/opt/gcc-arm-none-eabi-10-2020-q4-major/bin:$PATH \
    ./waf sub -j4
```

生成物通常位于：

```text
build/sitl/bin/ardusub
build/Pixhawk1/bin/ardusub
build/Pixhawk1/bin/ardusub.apj
```

如果换了电脑或仓库位置，不要硬编码上述工具路径，应先检查该环境的 Python 依赖和 ARM GCC。

## 7. 不同修改对应的最低验证

| 修改类型 | 最低验证 | 额外要求 |
|---|---|---|
| 纯 Markdown | 链接检查、`git diff --check` | 技术描述仍须对照源码 |
| ArduSub 车辆逻辑 | SITL 编译、相关场景 | Pixhawk1 编译 |
| 公共库 | 受影响目标编译 | 检查其他调用者，不能假设只有 Sub 使用 |
| 新模式或控制器 | SITL 模式切换和输入超时 | 无推进器台架测试，再做水池测试 |
| MAVLink | XML/生成链、发送接收两端 | 检查消息 ID、路由、频率和兼容性 |
| 传感器后端 | 解析测试、单位/坐标/时间测试 | 断线、坏帧、超时和质量下降测试 |
| HAL/hwdef/板卡 | 对应板卡固件编译 | 原理图核对、无桨台架验证 |
| 解锁/失控保护/电机输出 | 编译远远不够 | 必须人工审查和分级实物验证 |

## 8. 禁止擅自进行的操作

- 不要删除、覆盖或回滚用户已有但尚未提交的修改。
- 不要因为当前不用某个驱动，就认定整个一级库可以删除。
- 不要直接编辑 `build/` 中的生成文件。
- 不要直接修改 `modules/` 子模块来伪装主仓库功能已经完成。
- 不要改变现有参数索引、含义或存储布局。
- 不要绕过 `AP_*_ENABLED`、解锁检查、failsafe 或输出安全层。
- 不要编造 MAVLink 消息、参数、驱动 API、测试结果或硬件引脚。
- 不要只因为编译通过就宣称传感器、控制器或实船功能验证成功。
- 不要未经用户确认执行大规模删除、目录迁移、强制 Git 操作、提交或推送。
- 不要把教学仓库变成与官方源码完全脱节的伪实现。

## 9. 完成任务时的交付格式

最终回复至少应包含：

1. 已经得到的结果；
2. 修改了哪些文件，以及每个文件为什么需要修改；
3. 核心调用链或数据流；
4. 实际执行过的构建和测试；
5. 尚未验证的部分和真实风险；
6. 是否提交、是否推送；
7. 学习者下一步应该阅读哪个文件或做哪个实验。

本地文件应尽量提供可点击路径。不得要求用户从前面的过程消息中自行拼接最终结论。

## 11. 本文的维护规则

当以下长期决策发生变化时，应同步更新本文：

- 主控板卡和工具链；
- 必需传感器及其接入方式；
- 香橙派与 Pixhawk 的职责边界；
- 保留或删除的飞行模式；
- MAVLink dialect 策略；
- 已建立的新驱动、新板卡或新的最低测试标准。

临时实验、尚未确认的设想和一次性的构建结果不应写成永久事实。它们应记录在对应实验文档、Issue 或提交说明中。
